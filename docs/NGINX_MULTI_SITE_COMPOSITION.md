# Nginx multi-site composition and conflict hardening

This Issue #14 increment adds bounded multi-site assembly to the existing Phase 2 engine. It does not add capability shelves, migrate the legacy generator, change the UI, or perform deployment.

## Additive request model

`composeNginxSites()` accepts the existing `profile` and `target` fields plus `sites`. The legacy `composeNginxCapabilities()` contract and its generated bytes remain unchanged.

```ts
composeNginxSites({
  profile: 'full-config',
  target: {version: '1.26.3', modules: ['http_proxy', 'http_map']},
  sites: [{
    id: 'customer-a',
    capabilities: [
      {id: 'reverse-proxy', input: {domain: 'a.example.com', targetHost: '127.0.0.1', targetPort: 3000}},
      {id: 'websocket', input: {routes: ['/']}},
    ],
  }],
});
```

Site IDs are 1–63 lowercase letters, digits, and internal hyphens, must begin with a letter, and must be unique. A request contains 1–16 sites and no more than 256 planned routes in total. Each site uses the same closed capability registry and schemas as the single-site API. Unknown fields fail closed.

Sites are sorted by ID before planning. Capabilities and routes retain their established canonical ordering, so permutations of equivalent site, capability, and route inputs produce byte-identical artifacts. AST provenance, explanations, prerequisites, and diagnostics carry the owning site ID; shared-resource explanations list all dependent sites.

## Shared HTTP resources

Each site contributes typed AST nodes. HTTP-level nodes are merged by a trusted semantic identity such as the destination variable of a `map`, then compared by normalized node structure with provenance excluded. Identical WebSocket maps are emitted once. The same identity with a different definition is a static `composition.shared.conflict` and no artifacts are returned. Rendered-text equality is not the ownership rule.

For `full-config`, shared resources appear once inside `http`. For `site-fragment`, all server blocks are written to one primary `site.conf`; when required, one supporting `http-shared.conf` is emitted. Operators must include `http-shared.conf` exactly once in the enclosing `http` context before including `site.conf`.

## Listener and virtual-host rules

The supported model uses exact validated DNS names and implicit wildcard-address listeners:

- independent exact names may share port 80 or share `443 ssl`;
- one exact name may use HTTP and HTTPS on different listener ports;
- the same exact name cannot be owned by two sites on the same port, including a TLS redirect server colliding with another port-80 site;
- all declarations for one listener must agree on plain versus SSL mode;
- duplicate default servers for a listener are rejected by the structural validator;
- duplicate literal locations within a site continue to be rejected;
- strip-prefix routes must end in `/`, preventing ambiguous replacement semantics.

Nginx selects an address/port first and then a server name. It permits multiple exact names on a shared listener. A duplicate name may be parser-accepted with a warning and ignored, so Forge rejects that ambiguity as policy before serialization. `default_server` is a property of `listen`; multi-site composition does not expose it. Deterministic site ordering makes the first implicit default stable, but callers must not treat that fallback as a configured catch-all.

Wildcard names, regular expressions, address-specific listeners, arbitrary listen options, user-selected default servers, multiple names per site, and other advanced matching are unsupported. They are rejected by the closed request and argument schemas instead of being approximated. These rules follow the official [request-processing](https://nginx.org/en/docs/http/request_processing.html), [`server_name`](https://nginx.org/en/docs/http/server_names.html), and [`listen`](https://nginx.org/en/docs/http/ngx_http_core_module.html#listen) documentation.

## Compatibility, validation, and security

The implementation uses the existing capability definitions, dependency checks, typed Phase 1 AST, directive registry, serializer, Forge artifact checks, and four-tier validation model. It never concatenates caller-provided configuration snippets. Domains, hosts, ports, paths, routes, booleans, and identifiers retain strict typed validation. Generation is pure and performs no filesystem, network, command, reload, restart, or deployment operation.

CI extends the immutable-digest-pinned Nginx matrix with multi-HTTP, multi-HTTPS, shared-WebSocket-map, mixed, fragment-bundle, and site-order fixtures. A separate warning fixture records that Nginx accepts a duplicate server name with a warning while Forge rejects it. Contradictory shared declarations have both Forge-policy and native negative coverage. Browser results still report native validation as `unavailable`, and target-host validation remains `not-run`.

## Migration and remaining Issue #14 work

Existing callers do not need to migrate. New callers choose `composeNginxSites()` only when assembling multiple sites. A one-site multi-site request emits the same configuration content as the equivalent legacy composition request, while adding site-aware metadata.

Remaining work includes any approved Phase 4 capability shelves and later product integration. TLS policy expansion, WebSocket convenience inference, load balancing, caching, security headers, compression, rate limiting, static-site composition, advanced virtual-host matching, deployment, and target-host readiness are not implemented here.
